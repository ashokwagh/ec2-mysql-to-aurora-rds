Reference Guide

Migrating a self-managed MySQL database to Amazon Aurora

An end-to-end runbook for moving a large MySQL database off an EC2 instance and onto a managed Aurora MySQL cluster — including the secure VPC network it should live in — using a snapshot-and-replicate strategy.

00 Overview

What this guide does, and when to use this approach.

This is the manual migration path used when a database is too large for AWS Database Migration Service (DMS) to handle reliably. Instead of copying table-by-table through a replication instance, you take one consistent backup, load it into Aurora, and then let Aurora catch up on everything that changed since — using native MySQL binary-log replication. A short cutover at the end switches the application over.

The two halves

A proper migration is really two projects. The network — a VPC with public and private subnets, NAT for outbound access, and a bastion for administration — so the new database lives somewhere secure. And the data move itself. Parts 1–8 below cover both, in order.

Before you start

  • Engine compatibility — the target Aurora MySQL major version must be compatible with the source MySQL major version (for example, source MySQL 8.0 → Aurora MySQL 3.x, which is 8.0-based).
  • Measure the database — total size and the largest tables. This drives the backup method and the expected catch-up time.
  • Agree a downtime budget — the only real downtime is the final cutover, usually a few minutes. Pick a low-traffic window.
  • Freeze schema changes — avoid DDL on the source during the migration; it can break replication.
Adapt to your project

A Target architecture

Where everything ends up, and why.

The design splits the VPC into a small, exposed public zone and a protected private zone, spread across two availability zones. Nothing valuable is directly reachable from the internet.

The bastion host is the single controlled SSH entry point. The NAT instances (one per availability zone) let private servers reach the internet outbound — for patches and API calls — while blocking unsolicited inbound traffic. The Aurora cluster and application servers sit in private subnets with no public IP.

NAT instance vs NAT gateway

AWS offers a managed NAT Gateway (simple, reliable, but ~$32+/month each plus data charges) and the self-managed NAT instance (a tiny EC2 box, far cheaper, but you patch it yourself). Either works — choose based on budget and how much you want to manage.

01 Build the network

Stand up the VPC the database will live in.

Skip this part if you already have a VPC with private subnets, NAT, and a bastion. Otherwise, build it in this order — each step depends on the one before it.

  1. Create the VPC with a CIDR block such as 10.0.0.0/16.
  2. Create four subnets — two public and two private, one of each in two availability zones (e.g. ap-south-1a and ap-south-1b).
  3. Create an Internet Gateway and attach it to the VPC.
  4. Route tables — a public route table with 0.0.0.0/0 → Internet Gateway, associated with the two public subnets. A private route table per AZ (you fill in its internet route in the next step).
  5. Launch the NAT — one NAT instance (or NAT Gateway) in each public subnet. For a NAT instance, you must disable the source/destination check, or it cannot forward traffic: 
    aws ec2 modify-instance-attribute \
  --instance-id [nat-instance-id] --no-source-dest-check
  6. Finish the private route tables — in each one, add 0.0.0.0/0 → [that AZ's NAT].
  7. Launch the bastion host — a small instance in a public subnet, with a public IP (or Elastic IP).
  8. Security groups — bastion: inbound SSH (port 22) from your office/home IP only. Private instances: inbound SSH allowed from the bastion's security group, never from the internet.
Optional but worth it

Add an S3 VPC endpoint. Backup traffic to S3 then stays on the AWS network instead of going out through NAT — faster and cheaper for a large database transfer.

02 Prepare the source database

Make the EC2 MySQL ready to be copied and replicated from.

Enable binary logging

Binary logging is what lets Aurora replay changes later. Edit the MySQL config (/etc/my.cnf or /etc/mysql/my.cnf):

[mysqld]
server-id        = 1
log_bin          = /var/log/mysql/mysql-bin.log
binlog_format    = ROW
binlog_row_image = FULL
bind-address     = 0.0.0.0

The bind-address change is critical: with the default 127.0.0.1, MySQL listens only for local connections and Aurora could never reach it. 0.0.0.0 makes it listen on the network — safe here because the instance is in a private subnet and the security group restricts who can connect.

Set retention, create the replication user

Set binlog retention generously so logs are not purged before Aurora finishes catching up, then create the user Aurora will log in as:

-- keep binlogs for 7 days
SET GLOBAL binlog_expire_logs_seconds = 604800;

CREATE USER 'repl_user'@'%' IDENTIFIED BY '[strong-password]';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl_user'@'%';
FLUSH PRIVILEGES;

Restart MySQL so bind-address takes effect, then confirm:

SHOW VARIABLES LIKE 'log_bin';        -- expect ON
SHOW MASTER STATUS;                   -- note File + Position

Finally, open the source's security group for port 3306 inbound from the Aurora security group or its subnet range.

03 Back up the database

Take one consistent copy — without straining production.

The job of the snapshot worker — a temporary, powerful, memory-optimized instance — is to produce the backup off to the side, so the live production server is never loaded.

  1. Snapshot the production data volume. Take an EBS snapshot of the volume holding the database files.
  2. Create a volume from that snapshot and attach it to the snapshot worker. The worker now holds a frozen, consistent copy.
  3. Back it up on the worker. For a large database, a physical backup with Percona XtraBackup is fastest: 
    xtrabackup --backup  --target-dir=/backup/full --user=root --password=[pw]
xtrabackup --prepare --target-dir=/backup/full
  4. Record the binlog position. XtraBackup writes it to xtrabackup_binlog_info — the binlog file name and position. You need this exact pair in Part 5.
  5. Upload to S3: 
    aws s3 cp /backup/full s3://[my-db-migration]/full/ --recursive
Alternative: logical backup

For a smaller database, a logical dump works too: mydumper for a parallel dump, or mysqldump --single-transaction --master-data=2 (the --master-data=2 flag records the binlog position into the dump). Physical backups scale better for large data.

04 Create & load Aurora

Stand up the cluster and load the bulk of the data.

  1. In the RDS console, choose Create database → Restore from Amazon S3.
  2. Select Aurora MySQL with a compatible engine version.
  3. Point it at the S3 location holding the XtraBackup files. Aurora builds the cluster directly from them.
  4. Place it in your VPC's private subnet group; attach the security group from Part 2.
  5. Wait for the cluster status to reach Available. This creates the cluster and its first instance — the writer.
  6. Add a reader instance for high availability and read scaling. It attaches to the shared cluster storage — no data copy needed.
If you used a logical dump

Create an empty Aurora cluster instead, then load the dump with mysql or myloader pointed at the cluster's writer endpoint.

05 Binlog delta sync

Close the gap between the backup and "now".

The backup is a snapshot from a moment in the past. While you were backing up and loading, the live database kept taking writes. Binary-log replication replays every one of those changes into Aurora and then keeps it current in real time.

On the Aurora writer endpoint, register the source as an external master using the binlog coordinates recorded in Part 3, then start replication:

CALL mysql.rds_set_external_master(
  '[source-host-or-ip]', 3306,
  'repl_user', '[strong-password]',
  '[binlog-file]', [binlog-position], 0);

CALL mysql.rds_start_replication;

Monitor the catch-up — watch the lag fall toward zero:

SHOW REPLICA STATUS\G   -- older Aurora 5.7: SHOW SLAVE STATUS
  • Replica_IO_Running and Replica_SQL_Running — both should be Yes.
  • Seconds_Behind_Source — should trend toward 0.
  • Last_IO_Error / Last_SQL_Error — should be empty.

06 Validate

Confirm the two databases agree before you commit.

  • Row counts — compare counts on the largest and most important tables, source vs Aurora.
  • Checksums — run a tool such as pt-table-checksum for a deeper integrity comparison.
  • Application test — point a staging copy of the application at the Aurora reader endpoint and confirm queries behave correctly.
  • Spot-check — verify routines, triggers, and views came across, not just table rows.

07 Cut over

The short, planned switch to Aurora.

Do this in the agreed maintenance window. With replication already near zero lag, downtime is only a few minutes.

When the source is read-only and Seconds_Behind_Source shows 0, Aurora has every last change. Detach it from the old master:

CALL mysql.rds_stop_replication;
CALL mysql.rds_reset_external_master;

Then repoint the application's connection string (or DNS) to the Aurora cluster writer endpoint, bring the app out of maintenance mode, and monitor error rates and latency closely for the first hour.

08 Clean up & harden

Finish the job and secure the result.

  • Terminate the snapshot worker. It is temporary and expensive — terminate it, do not just stop it (a stopped instance still bills for its storage).
  • Keep the old database as a fallback for a few days (stopped, not deleted) in case a rollback is needed. Decommission once confident.
  • Delete the temporary S3 backup files.
  • Harden Aurora — automated backups, a sensible retention period, CloudWatch alarms, and Performance Insights.
  • Remove the temporary rule that allowed Aurora → source on port 3306.

V Verification checks

How to confirm each piece is actually doing its job.

Is a NAT instance being used?

A NAT instance does nothing on its own — its use lives in a route table. In the VPC console, open a private subnet's route table and look at the 0.0.0.0/0 route. If its target is a NAT instance, everything in that subnet uses it. Also confirm the NAT instance has source/destination check disabled, and check its NetworkOut metric for live traffic.

Is the bastion being used?

The bastion's job is defined by a security-group chain: its own group allows inbound SSH from approved IPs, and the private instances' groups allow inbound SSH from the bastion's group. To see live use, connect to the bastion and run last — it lists recent SSH logins.

What phase is the migration in?

Connect to the Aurora writer endpoint and run SHOW REPLICA STATUS\G. Running replica threads pointed at the EC2 source mean the delta sync is live and cutover has not happened. No replication configured means it is either pre-sync or already cut over.

! Common pitfalls

The mistakes that most often derail this migration.

Binlog purged too early

If the source purges binary logs before Aurora catches up, replication breaks and the initial load must be redone. Set retention generously in Part 2.

Wrong binlog format

binlog_format must be ROW. Statement-based logging causes subtle replication inconsistencies.

DDL during migration

Schema changes on the source mid-migration frequently break replication. Freeze DDL until after cutover.

Forgotten essentials

Version incompatibility between source and Aurora; a security group that does not allow Aurora to reach the source on 3306; or forgetting that bind-address changes need a MySQL restart.
